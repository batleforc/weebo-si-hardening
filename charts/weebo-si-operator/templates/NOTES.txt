  kind: WeeboSiConfig

    features: {}
  EOF

Then follow the five-step rollout in docs/bricks/weebo-si-operator.md (mode: DryRun with a
catalogue and default, then spec.teams, then mode: Enforce scoped to a pilot namespaceSelector,
then remove the selector).

Check readiness:

  kubectl -n {{ .Release.Namespace }} rollout status deployment/{{ include "weebo-si-operator.fullname" . }}-webhook
  kubectl -n {{ .Release.Namespace }} rollout status deployment/{{ include "weebo-si-operator.fullname" . }}-controller

Break-glass, if the operator itself is the thing that's broken (failurePolicy: Fail means an
unavailable webhook blocks every write it covers — DevWorkspaces, Pods, policy objects —
cluster-wide). Every webhook configuration this release rendered carries its instance label, so
one command removes them all; `helm upgrade` puts them back once the operator is healthy:

  kubectl delete mutatingwebhookconfiguration,validatingwebhookconfiguration \
    -l app.kubernetes.io/instance={{ .Release.Name }}

{{- else }}

*** networkPolicy.enabled is false. ***
Nothing in this release limits who can reach the webhook (port {{ .Values.webhook.service.targetPort }}) or the metrics
port ({{ .Values.metrics.service.port }}): any pod your cluster's network allows can. To fence them, set:

  networkPolicy.enabled=true
  networkPolicy.kubeApiserver.cidrs     the apiserver's addresses (kubectl get endpoints kubernetes -n default)
  networkPolicy.kubeApiserver.ports     its endpoint port(s), default 443 and 6443
  networkPolicy.monitoring.*Selector    your metrics scraper (default: namespace "monitoring")
  networkPolicy.dns.*Selector           your cluster DNS (default: kube-dns in kube-system)

The render fails without kubeApiserver.cidrs (or apiserver selectors), since a policy that drops
the apiserver's calls blocks every write the webhook covers.
